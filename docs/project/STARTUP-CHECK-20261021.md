# Windows 启动与窗口检查（2026-10-21）

## 本轮改动

- Windows 打包版移除默认应用菜单，正常启动不显示 File/Edit/View/Window/Help；内部调试开关仍可临时启用菜单。
- Controller 与静态 Web 服务并行启动。新增 `/api/internal/desktop/ui-ready`，仅用于确认配置 API 可以工作；原 `/ready` 的完整运行健康语义不变。
- 配置界面不再等待微信服务完成启动；隐藏的 OpenClaw、Control Plane 和诊断页面在首次访问时才加载。
- 工作台在 DOM 就绪时显示，不等待所有图片完成；主文档加载失败仍提供重新加载。
- 去掉首次准备时强制播完的 23 秒视频，换为没有最低等待时长的 Bridge 状态卡。Windows 解压版通常不会触发运行归档解压动画，此项不能当作本次 Windows 实测节省 23 秒的依据。
- 代理诊断移到后台，每个解析最多等 1500ms；诊断只检查本机地址，不影响窗口和配置返回。

## 测量方法

在同一台开发机上运行 Windows 解压版，使用空白 Electron 用户目录和同一个本机配置目录。无模型密钥和微信授权，没有发送微信消息或调用付费模型。未重启操作系统或清除文件缓存，因此属于本机连续启动对照，不能代表所有用户设备的冷启动性能。

从启动 exe 前记录的 UTC 时间，到实际嵌入工作台出现 Bridge 导航及首页标题，记录界面可见时间；另检查 webview 的透明度为 1。通过打包版主进程日志中的 `Windows menu bar visible=false` 验证菜单状态。

旧版 `ad163f1` 的一次对照为 **13.474 秒**。第一版优化 `5a14273` 的一次对照为 **1.052 秒**；这时 `/ui-ready` 为 true，完整运行状态仍是 `stabilizing-runtime`、ready=false，说明配置界面已经能够独立打开，而非把微信服务误报为就绪。

最终代码 `e994749` 重新打包后，连续两次测量如下。第二次复用第一次的 Electron 用户目录，但每次都完全退出后台后再启动。

| 测量 | 首页出现 | 完整运行健康与首页自动更新均就绪 |
| --- | --- | --- |
| 最终版第一次 | 1.137 秒 | 14.299 秒 |
| 最终版第二次 | 0.985 秒 | 14.186 秒 |

两次均确认菜单隐藏、启动时只挂载一个工作台 webview、完全退出后测试端口和后台进程释放。首次页面显示时完整运行健康仍未就绪；首页明确显示“本地服务正在启动”，允许先配置 API，并自动切换到“本地服务已就绪”。只有模型和实际环境均就绪后才允许扫码。unhealthy/degraded 或读取失败仍提供故障恢复入口。

这轮主要消除了工作台等待后台的阻塞，**不能宣称微信后台的完整启动也缩短为约一秒**。本机完整运行准备仍需约 14 秒；要进一步缩短这一部分，需继续分析本地运行内核和稳定检查的耗时，不能省略健康检查冒充提速。

## 验证范围

类型检查、Biome 检查、就绪路由、代理诊断超时、首次加载、延迟加载页面与首页状态的 37 项定向测试已通过。Windows 解压版已独立构建和启动。真实微信收发、付费模型调用、干净系统安装器和签名仍按 ROADMAP 另行验收。
